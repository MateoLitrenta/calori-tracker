# Calori V9.1 — Preparación de staging real

## Estado y límites

Rama desde `main` **b95c75c**, después de los merges #70 y #71. Se propone un **proyecto Supabase independiente y vacío**, `calori-security-staging-v9-1`, para ensayar el esquema completo y el endurecimiento sin enlazar despliegues a Production. No se creó proyecto/rama, no se ejecutó SQL remoto ni se consultaron/exportaron datos personales. No cambian la app, sus credenciales, migraciones activas o Production.

El usuario confirmó para `calori`: cero perfiles mixtos, días con perfil incorrecto y comidas/ejercicios asociados a días ajenos; ejecución completa de `010_checks.sql` en READ ONLY/REPEATABLE READ con row_security=off y rollback, sin errores; cero ramas y cero filas de historial de migraciones. Son **resultados aportados por el usuario**, no consultas repetidas en esta tarea. No equivalen a aplicar `020_upgrade.sql`, ni a demostrar que las siete migraciones estén ausentes: pueden haberse aplicado manualmente.

La propuesta está en `supabase/proposals/staging-v9-1`, **fuera de `supabase/migrations`**. El bootstrap rechaza objetos Calori preexistentes, exige reconocimiento explícito y prerrequisitos administrados por Supabase; nunca crea `auth`/`storage`, sus funciones o usuarios. Reproduce intencionalmente el esquema legacy para ensayar legacy→hardened, incluidos OR y grants excesivos conocidos. **No es un baseline seguro para exponer a usuarios externos ni una migración para Production.**

Se rechaza cualquier tabla previa en public, el esquema ai_private preexistente o buckets avatars/meal-photos ya creados. Las migraciones de fotografías tienen ON CONFLICT DO UPDATE: este guard evita que un bootstrap de ensayo reconfigure silenciosamente buckets existentes. No se borran ni normalizan esos objetos para continuar.

## Inventario y reconstrucción

Las siete migraciones actuales dependen de cuatro tablas no creadas en la cadena. Ninguna instala Supabase Auth, Storage, sus roles o configuración externa.

| Migración | Dependencias previas | Aporta |
|---|---|---|
| 202609100001 | profiles | activity_level, default, NOT NULL y CHECK |
| 202609110001 | profiles/daily_logs/meals/workouts, auth.uid | reset transaccional invoker y EXECUTE autenticado |
| 202609250001 | profiles, storage.buckets/objects, auth.uid | avatar_path, CHECK, bucket privado avatars 512 KiB, JPEG/WebP y cuatro políticas |
| 202609290001 | meals y Storage | photo_path, CHECK, bucket privado meal-photos 1 MiB, JPEG y cuatro políticas |
| 202609290002 | profiles | onboarding_completed: legacy true; nuevos perfiles false |
| 202610090001 | auth.users y service_role | ai_private.daily_usage con RLS, RPC de cuota server-only y grants/revokes |
| 202610130001 | auth.users/auth.uid, roles, PL/pgSQL | coach_goals, índices, RLS/ACL de columnas, trigger, versión y límite concurrente |

`000_initial_schema.sql` aporta profiles/daily_logs/meals/workouts, PKs, UUID/FKs simples a Auth/perfiles/días, UNIQUE(user_id,date), columnas de negocio, RLS legacy y grants descritos. Las migraciones posteriores añaden sus propias columnas/constraints/buckets/funciones; no se duplican ni reimplementan. `010_bootstrap.psql` incluye literalmente las siete en orden y ejecuta el preflight real al final. Un test exige igualdad con la lista completa del directorio: agregar una migración obliga a revisar la secuencia.

Coincide con el catálogo documentado en #71 en: cuatro ENABLE RLS sin FORCE; profiles autorizado por id OR user_id; identificadores independientes; profile_id y fechas de hijos nullable; FKs simples; grants amplios anon/authenticated y buckets privados tras migrar. **No es un dump remoto exacto**: tipos/defaults de negocio, nombres de índices/políticas y acciones de FKs no completamente entregados se proponen desde el fixture documentado y consumidores actuales. Se elige NO ACTION para las FKs, sin presumir que todas las remotas sean iguales; el upgrade preserva las acciones que encuentra. El `001_clean_baseline.sql` anterior usa igualdades/FKs/NULLs diferentes y no sustituye esta reconstrucción.

Queda cotejar metadatos completos de tipos/defaults, FKs/acciones, ACL/default privileges/roles heredados y definiciones/versiones de cuotas/objetivos/servicios. El preflight exitoso aportado prueba sus chequeos, no todos esos detalles. No se inventan triggers, extensiones o funciones iniciales ausentes del inventario. Si aparece otra dependencia, detener y revisar la propuesta; no ampliar permisos ni rellenar datos silenciosamente.

Verifica ausencia de tablas de aplicación en esos shims, rollback de bootstrap inyectado, rechazo de target ocupado, las siete migraciones, seis tablas con RLS, tres funciones, ocho políticas de fotografías, buckets/defaults, dos propietarios, cuotas y objetivos, preservación tras 020 y recuperación 040. La ejecución focalizada inicial aprobó 10/10 en PostgreSQL/PostgREST locales Windows. El workflow `staging-schema-v9-1.yml` ejecuta además los 38 archivos (434 casos esperados), TypeScript frontend/endpoints, lint, build y diff check en Linux con Node 24.4.1, PostgreSQL 17.5 y PostgREST 16.5 oficiales verificados por hash. **Resultados finales y códigos en `staging-security-v9-1-validation.json`**, cuando finalice CI. ## Elegir y autorizar el entorno

**Recomendado: proyecto independiente.** Nombre `calori-security-staging-v9-1`; misma región y versión PostgreSQL compatible con Calori, confirmadas en Dashboard; propietario y fecha de cierre asignados. No copiar Production, backups o usuarios reales. Auth/PostgREST/Storage deben inicializarse normalmente en Supabase antes del SQL. Sin integración GitHub→DB ni vínculo Vercel Production: evita que el historial remoto vacío dispare replay/merge de cambios por error.

**Alternativa: rama persistente**, `security-staging-v9-1`, con ref/credenciales propios y sólo datos sintéticos. No crear ni hacer merge/rebase/reset de una rama ahora. Con historial remoto vacío no asumir que un branch vaya a reconstruir correctamente el esquema: el modo de creación, custom roles y fuente de migraciones/dump deben verificarse antes de elegirlo. Si la rama ya trae tablas, el bootstrap debe rechazarla; no vaciarla ni forzar su ejecución. No utilizar merge de Supabase para desplegar este ensayo a Production.

Costos de referencia consultados el 2026-11-03: Micro **US$0,01344/h**, aproximadamente US$0,323 por 24 h o US$10/mes de cómputo continuo; más disco, Storage, egress, Auth u otros consumos según plan. Los créditos de cómputo pertenecen a la organización y pueden estar consumidos por Production; no prometer un segundo proyecto gratuito. Preview Branching también parte de esa tarifa Micro y **no está cubierto por Spend Cap**. La oferta real y el costo de una rama persistente deben confirmarse en Dashboard antes de aprobar. Fijar un ensayo de 24 h, responsable, revisión de consumo y cierre manual; una alarma no es un tope duro. No activar PITR, IPv4, dominios o upgrades pagos sin otra aprobación. [Compute](https://supabase.com/docs/guides/platform/manage-your-usage/compute), [Branching usage](https://supabase.com/docs/guides/platform/manage-your-usage/branching).

## Procedimiento de ensayo, después de autorización

1. Aprobar proyecto/rama, ref exacto, región/versión, costo máximo operativo y fecha de eliminación. Registrar el ref de Production **ziclplqhbrpvcqjjqoau** como denegado. Confirmar visualmente el ref de staging en Dashboard y conexión SQL; no tomar el nombre como prueba de identidad. Preparar DSN/password fuera de Git/chat/logs, mediante un archivo de servicio PostgreSQL y passfile privado. No imprimir connection strings. Configurar un servicio local `calori_staging` con host/ref revisados y TLS `verify-full`/CA del proveedor.
2. En staging vacío, revisar prerrequisitos administrados y el SQL del commit aprobado. Con psql 17 ejecutar `psql "service=calori_staging" -X -v ON_ERROR_STOP=1 -f supabase/proposals/staging-v9-1/010_bootstrap.psql`. El archivo lleva un reconocimiento explícito pero **no autentica el host**; el operador debe comprobarlo antes. Aborta si ve tablas existentes. Baseline atómico; las migraciones existentes mantienen sus propios límites de transacción, por lo que NO se promete atomicidad de toda la cadena. Ante fallo tardío, conservar logs sanitizados y recrear sólo el staging sintético con autorización; no reintentar a ciegas una secuencia parcial.
3. Registrar commit, checksums de los ocho archivos y catálogo resultante. No conectar GitHub/Supabase automático todavía: este replay manual no registra historial CLI. Para adoptar historial, proponer aparte el baseline con timestamp anterior a la primera migración mediante CLI y cotejar cada versión/checksum; cualquier reparación de historial será explícita y sólo del staging comprobado. **No ejecutar db push/reset/migration repair contra Production** por tener historial cero. No copiar el baseline a la cadena activa en este PR.
4. En Auth del staging crear exactamente dos cuentas confirmadas: `calori-staging-a@example.test` y `calori-staging-b@example.test`, con contraseñas aleatorias distintas (≥16 caracteres) guardadas en un gestor/entorno local. El alta administrativa de cuentas sintéticas se autoriza junto al ensayo, sin SMTP real ni invitaciones a terceros. No usar cuentas personales. Para probar registro/verificación de email, habilitar después un buzón/SMTP de ensayo aislado o el inbox del stack local y repetir el flujo de las cuentas; el alta administrativa no certifica signup o recuperación de contraseña.
5. Preparar las variables de la siguiente sección fuera de Git. Ejecutar `node scripts/staging/real-services.mjs seed`. Los datos usan IDs estables y un recibo privado con fecha/propietarios, sin passwords/tokens. Dos días por cuenta con comidas, ejercicios, agua, pasos, peso, fotos, avatar y objetivos de frecuencia/pasos. Las fotos se suben por Storage real; los registros, por PostgREST; los tokens provienen de signInWithPassword real. No se inserta en auth.users ni storage.objects mediante SQL remoto. Las altas requieren identidad retornada y los reintentos explícitos preservan IDs y perfil existente. Si una operación queda incierta, conservar recibo y revisar sólo esas filas sintéticas. Más de siete días después, revisar fechas/objetivos antes de reutilizar el recibo.
6. Tomar respaldo restaurable del staging según la sección siguiente. Ejecutar preflight (`.../security-rls-v9-1/000_preflight.sql`), revisar resultado, y **sólo entonces** `020_upgrade.sql` y `030_postflight.sql`, con psql/ON_ERROR_STOP. El upgrade vuelve a comprobar bajo locks y es transaccional. No fragmentarlo en el SQL Editor. No ejecutar 001_clean_baseline o 002_atomic_records.
7. Tras postflight satisfactorio, reconocer `CALORI_STAGING_POSTFLIGHT=passed` y ejecutar `node scripts/staging/real-services.mjs verify`. Comprueba sign-in/getUser/refresh, propias/ajenas, confirmaciones, asociación ajena rechazada, lecturas anidadas, descarga privada por signed URL propia/denegación ajena y versión esperada de objetivos con restauración del target. No registra tokens, URLs firmadas o respuestas sensibles; cierra sólo sus sesiones. El fallo de una prueba bloquea el ensayo. La prueba de asociación elimina su fila de sondeo si un backend vulnerable la admitiera; cualquier otra anomalía se revisa en ese entorno sintético antes de continuar.
8. Ejecutar la revisión de frontend y de uploads descrita abajo. Guardar un acta con pasos/resultados y metadatos de versión, sin credenciales ni datos personales. No marcar servicios remotos verificados sólo porque el script exista.
9. Ensayar recuperación en el staging: detener clientes/escrituras de prueba, ejecutar `040_readonly_recovery.sql`, reconocer `CALORI_STAGING_RECOVERY=applied` y ejecutar el modo `readonly`. Comprueba lectura propia y rechazo de escritura propia de comida. **040 sólo restringe las cuatro tablas base:** objetivos, cuotas, Auth y Storage siguen con sus permisos separados. No llamarlo mantenimiento global. Para una ventana real se debe controlar también esos escritores mediante un mecanismo aprobado. Mantener las restricciones correctas; reparar hacia adelante o reconstruir el staging, sin reinstalar políticas vulnerables ni conceder ALL para seguir probando.

## Variables y guards de los scripts (no configuradas en esta tarea)

- CALORI_STAGING_PROJECT_REF: ref nuevo, nunca el de Production.
- CALORI_STAGING_URL: exactamente https://<ref>.supabase.co, sin userinfo, query, fragment o puertos alternativos.
- CALORI_STAGING_PUBLISHABLE_KEY: publishable/anon de staging; se rechazan sb_secret y JWT de service_role.
- CALORI_STAGING_ACK: synthetic-only:<ref>.
- CALORI_STAGING_EMAIL_A/B y CALORI_STAGING_PASSWORD_A/B: sólo las dos cuentas dedicadas.
- CALORI_STAGING_FIXTURE_FILE: ruta absoluta privada, con directorio existente fuera de **cualquier** repositorio Git; el recibo no contiene contraseñas, tokens o URLs firmadas. Proteger el directorio con permisos 0700/ACL equivalentes. No compartirlo en GitHub.
- CALORI_STAGING_POSTFLIGHT=passed o CALORI_STAGING_RECOVERY=applied, únicamente tras el paso real correspondiente.

Para un stack Supabase local real se admite exclusivamente `http://127.0.0.1:54321`, ref `local`, ACK synthetic-only:local y CALORI_STAGING_ALLOW_LOCAL=1. Ese stack debe inicializarse con un runtime/CLI oficial fijado y su configuración revisada, sin vincular Production; los shims del test no lo reemplazan. Ninguno de estos reconocimientos constituye autorización por sí mismo. Los guards evitan errores habituales de destino, no sustituyen la revisión humana de entorno/credenciales.

## Respaldo, restauración y paso posterior a Production

Antes del ensayo de upgrade: conservar commit/checksums, catálogo y ACL de aplicación, respaldo cifrado y recibo sintético; guardar también los bytes y checksum de cada objeto Storage. Ensayar restauración en otro destino descartable autorizado con Supabase inicializado, revalidando login, FKs, políticas y URLs de fotos. El seed permite reconstruir únicamente fixtures; **no sustituye demostrar un respaldo/restauración real**. No copiar DDL administrado de auth/storage de un shim a un proyecto real.

Para Production, con autorización posterior independiente: confirmar disponibilidad/retención del backup del plan, RPO/RTO, espacio de recuperación, responsables y ventana de mantenimiento de todos los escritores. El backup de DB **no contiene los archivos de Storage**, sólo sus metadatos; definir respaldo coherente de objetos, protección de secretos y restauración según el procedimiento oficial Supabase, sin exports en este PR. No restaurar una base antigua sobre escrituras posteriores sin decisión explícita de pérdida aceptable y reconciliación. Un pg_dump de shims sólo prueba SQL local y no certifica GoTrue/Storage administrados. [Backups oficiales](https://supabase.com/docs/guides/platform/backups).

La secuencia eventual sobre Production será únicamente la propuesta de seguridad revisada: backup restaurable → mantenimiento aprobado → preflight fresco → 020 completo → postflight → pruebas con cuentas de ensayo autorizadas → reapertura gradual y monitoreo. **Nunca ejecutar el bootstrap ni las siete migraciones a ciegas sobre Production**. El inventario cero de inconsistencias puede cambiar antes de la ventana y debe volver a comprobarse con autorización. Antes de commit un fallo de 020 revierte; después, recuperación read-only y corrección hacia adelante. Restaurar un backup con políticas antiguas no autoriza reabrir usuarios con ese aislamiento vulnerable.

Requieren autorización: todos los recursos pagos y cambios remotos, configuración de servicios/Preview, creación/borrado de cuentas/objetos y cualquier intervención futura de Production.
